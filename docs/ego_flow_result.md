# `L_ego_flow` 訓練線 —— 結果與結論

> **狀態：陰性，2026-08-08 收束。** 三個訓練 run 一致顯示這一項讓 Sintel 的相機位姿變差。
> 本檔記錄數字、機制、以及過程中量到的幾個比陰性結果更有價值的東西。
>
> 設計與公式對照在 [monst3r_loss_diff.md](monst3r_loss_diff.md)；後處理（TTO）那條線見第 6 節。

---

## 1. 這條線做了什麼

[monst3r_loss_diff.md](monst3r_loss_diff.md) 記錄了前兩次移植 MonST3R 的失敗（`static_photo` 完全無效、`camera_smooth` 有效但不足）。這是第三次，也是唯一一次把**幾何式子逐行搬對**的：MonST3R 的視差形式 ego-flow（[ego_flow.py](../training/ego_flow.py)）、smooth-L1、逐像素離群丟棄。

**但 target 換成 GT 導出的 ego-flow，不是 RAFT。** 這個替換不是細節：MonST3R 的 RAFT target 有價值正是因為它**不知道 GT**，那是無標註優化下唯一的外部錨。換成 GT 導出之後，這是一個**像素空間、按視差加權的 reprojection loss**，不是 MonST3R flow loss 的移植——論文不得如此宣稱。

它相對 `L_cam` 的兩個結構性差異（不只是重新加權）：

- **逐對 vs 逐幀** —— `L_cam` 完全不約束相鄰幀的相對運動，而相對誤差正是累積成漂移、也是 RPE 在量的東西
- **像素空間 vs 參數空間** —— 誤差按可觀測性加權（近景視差大 → 平移明顯；遠景幾乎看不出來），這也是 bundle adjustment 最小化重投影誤差而非位姿參數誤差的理由

## 2. 三個 run 與基準

基準：`checkpoints/dyn_inst_temporal_smooth.pt`（= run 2 `dyn_vggt_v3_s1_inst_smooth_temporal` 的 `epoch_30.pt`，md5 `67bbebf4…`）。
所有數字同協定：`benchmark/eval_sintel.py`／trainer channel B，全序列不分塊，`max_depth=80`，14 個 pose 序列。

| run | 配置 | ATE | RPE-t | RPE-rot | AbsRel |
|---|---|---|---|---|---|
| **基準** | run 2 ep30 | **0.1343** | **0.0633** | **0.3943** | **0.1842** |
| 1 | 預測深度 + 解凍 `depth_head` + `L_depth` | 0.1557 (+15.9%) | 0.0629 (−0.6%) | 0.4399 (+11.6%) | 0.1926 (+4.6%) |
| 2 | **GT 深度**（單一變因） | 0.1433 (+6.7%) | 0.0603 (−4.7%) | 0.4184 (+6.1%) | 0.1956 (+6.2%) |
| 3 | GT 深度 + 無動態遮罩 | 0.1401 (+4.3%) | 0.0607 (−4.1%) | 0.4194 (+6.4%) | 0.1991 (+8.1%) |

（末 5 epoch 平均。run 2、3 各自相對前一列只改一件事，所以差值可歸因。run 1 同時改三件，不可歸因。）

### 那個 RPE-t 的「改善」是假的

`cave_2` 與 `temple_3` 的 ATE 是其他序列的 10 倍，主導平均值，而**兩者的數字都有已記錄的問題**：`temple_3` 的 `m_geo` 只留 7.8% 靜態像素（table.md 缺口 #9）、`cave_2` 的平移在光流中不可觀測（table.md 表 7，敏感度 0.455）。拿掉這兩個之後：

| | ATE mean / median | RPE-t mean / median |
|---|---|---|
| 基準 | 0.0500 / 0.0424 | **0.0306** / 0.0267 |
| run 2 | 0.0616 / 0.0628 | 0.0340 / 0.0316 |
| run 3 | 0.0602 / 0.0628 | **0.0334** / 0.0322 |

**12 個可信序列上每一個指標都變差**，RPE-t 平均 +9.2%。那個 −4.7% 完全由那兩個序列撐起。

## 3. 結論

**`L_ego_flow` 沒有改善相機位姿，是讓它變差。** 三個配置一致，且 run 2 是單一變因、基準以同一支腳本同一組協定量得。

---

## 4. 為什麼 —— 四條獨立的機制證據

1. **上界不足。** 用 TTO 直接最小化 flow 殘差（無泛化差距，是任何訓練 loss 的理論上界）：純 flow 最小化把殘差 2.13 → 0.57，**ATE 反而 0.1343 → 0.1630**；配上強 anchor 才拿到 0.1266（−5.7%）。上界低於訓練雜訊帶 ±0.02。
2. **殘差與目標不相關。** 同一個 flow 殘差對 `VGGT-1B` 和 `epoch_30` 幾乎相同，而後者的 ATE 好 21.6%（`diag/flow_pose_headroom.py` 檔頭）。要最小化的量分不出兩個品質差 21% 的模型。
3. **可觀測度天花板。** 平移在光流中的敏感度跨序列差 **85 倍**（0.068~5.799 px，table.md 表 7），旋轉只差 2.3 倍。低視差序列的平移誤差**物理上不在光流裡**。該測試目標無關，故此限制對 RAFT target 與 GT target 同時成立。
4. **訓練資料的位姿監督已飽和。** 見第 5.2 節，`loss_camera` 的 train/val 差距 **14.7×**。

第 4 條是最根本的：訓練集上幾乎沒有剩餘的位姿誤差可榨，任何在同一批資料上計算的新 loss 只能改變**往哪個方向過擬合**。這解釋了為什麼效果在 **ep1 就已出現**（換權重立刻位移，不是慢慢學）而之後只是一路漂移變差。

## 5. 過程中量到的、比陰性結果更有價值的東西

### 5.1 目標函數有 77% 花在 gate 上

run 2 最後一個 epoch 的加權組成：

| 項 | 加權後 | 佔比 |
|---|---|---|
| `loss_gate` | 0.1193 | **76.8%** |
| `loss_camera` | 0.0210 | 13.5% |
| `loss_ego_flow` | 0.0106 | 6.8% |
| `loss_camera_smooth` | 0.0045 | **2.9%** |

這是一個相機位姿的實驗，而所有跟 pose 有關的項加起來只有 20%。更麻煩的是 CLAUDE.md 自己就寫「判斷 gate 品質一律用 AUC/F1，不要用 BCE」—— **77% 的梯度花在一個我們自己不信任的量上**。此配比繼承自 run 1/2（產出目前最佳結果的配置），從未被消融過。

### 5.2 域差距 14.7×

| | train | val (Sintel) | 差距 |
|---|---|---|---|
| `loss_camera` | 0.0042 | 0.0619 | **14.7×** |
| `loss_gate` | 0.1193 | 0.9275 | 7.8× |
| `loss_ego_flow` | 0.4910 | 1.3341 | 2.7× |

這不是本線造成的——run 2 收斂時是同樣的比例，是整條 lineage 的既有狀態。

### 5.3 殘差裡 94% 是位姿誤差、6% 是深度誤差

同一個煙霧測試（同 warm start、同釘死的 clip 形狀）：預測深度 `loss_ego_flow` = 0.7933，換成 GT 深度 = 0.7485，**只差 5.6%**。

推論：(a) 用 GT 深度幾乎不損失訊號，卻切斷了「深度誤差與平移誤差互相抵銷」的作弊路徑（`disparity × t` 使全域深度尺度誤差可被平移尺度誤差完全抵銷，而平移尺度正是 ATE 在量的）；(b) MonST3R 的深度/位姿耦合在此本來就沒什麼可耦合的。

### 5.4 深度退化來自主幹漂移，不是深度頭訓練

| run | `depth_head` | `L_depth` | AbsRel |
|---|---|---|---|
| 1 | 解凍 | 開 | 0.1926 (+4.6%) |
| 2 | **凍結** | **關** | 0.1956 (+6.2%) |

run 2 完全沒有訓練深度，退化幅度卻與 run 1 相當。原因是解凍的 `global_blocks 8-23` / `temporal_blocks` 被 pose 目標帶偏，而深度頭讀的是同一批特徵。→ **`L_depth` 對深度沒有保護作用**，它只是額外的梯度來源（`Grad/depth_head` median 53 vs 相機路徑 2，run 4 的失敗量級）。

### 5.5 動態遮罩在 GT 深度配置下無作用，且丟掉最有訊號的像素

用 GT 深度時，物體自身的運動**在兩條 flow 裡都不存在**，動態像素的殘差就是純位姿誤差 → 遮罩不提供偏誤保護。而動態像素恰恰是最近的：

| 資料集 | 靜態中位深度 | 動態中位深度 | 比值 | 動態占比 |
|---|---|---|---|---|
| PO | 3.716 | 2.899 | 0.78× | 13.0% |
| Spring | 14.626 | 2.548 | **0.17×** | 31.9% |
| Sintel | 3.755 | 2.537 | 0.68× | 34.0% |

近 = 視差大 = 平移訊號最強。**遮罩扔掉的是 13~34% 最有資訊量的像素。** 但實測（run 3）關掉之後差異落在雜訊帶內——這個修正是對的，卻不足以改變結論。

## 6. 與 TTO（後處理）線的關係

**兩條線對 flow 的判定一致。** TTO 文件第 7 節第 1 條：MonST3R 的 flow 項單獨無效（0.1335 vs 基線 0.1343，改善 4/14）。訓練側三個 run 得到同一件事。

**TTO 真正有效的是平滑先驗與參考幀融合，不是 flow。** 其表 2 的 `no-flow + 二階` = 0.1176、`no-flow + 三階` 改善 14/14——大部分收益在完全沒有 RAFT 的情況下就拿到了。flow 的角色是「煞車而非動力」。

**為什麼 TTO 有空間而訓練沒有**：TTO 直接在目標序列上優化，**繞過第 5.2 節的域差距**。這不是「TTO 比訓練強」，是兩者面對的問題不同。

### 對 TTO 線做同樣的穩健性檢查（本檔第 2 節的方法）

用其表 4b 的逐序列數字重算：

| | ATE(14) | **ATE(12)（去掉 cave_2 / temple_3）** |
|---|---|---|
| base1 | 0.1343 | 0.0500 |
| 融合 K=5 | 0.1247 (−7.1%) | 0.0438 **(−12.4%)** |
| 融合 + 一階 | **0.0679 (−49.4%)** | 0.0426 (−14.6%)，8/12 |
| 融合 + 二階 | 0.1109 (−17.4%) | **0.0385 (−23.0%)**，11/12 |

三個結論：

1. **TTO 的改善撐得住這個檢查**（訓練線的不撐得住，這是兩條線最大的差別）。
2. **但 −49.4% 這個標題數字撐不住**：12 序列上只剩 −14.6%，`cave_2` 一個序列就貢獻了 14 序列平均改善的 83%。
3. **階數排序翻轉，且翻向保守解**：ATE(12) 是二階（−23.0%、11/12）優於一階（−14.6%、8/12），而一階在容易的序列上傷害很大（`sleeping_2` +372%、`market_2` +163%）。→ **建議論文主操作點用融合 + 二階。**

## 7. 建議的下一步（不是更多 loss 工程）

**把 `camera_smooth` 的權重拉高。** 兩條線獨立指向同一件事：

- TTO 側：平滑先驗單獨值 −23%（12 序列），且 GT 軌跡比 VGGT 預測平滑 **5~53 倍**（TTO 文件 6.2）——一個量大、方向明確、幾乎沒被使用的先驗
- 訓練側：它只佔目標函數 **2.9%**，而 gate 佔 76.8%

形式已經是對的：訓練側的 `compute_camera_smooth_loss` 是**二階**，而 TTO 顯示無 flow 時二階最好——訓練側沒有 flow 項，所以只需要調權重，不需要改形式。一個 run、約 26 小時、不動架構。

同時該把 gate 的權重壓下來——那 76.8% 從未被消融過。

## 8. 已知的坑（給後人）

| # | 坑 | 症狀 / 代價 |
|---|---|---|
| 1 | **基準取錯列** | table.md 第 368 列是 `s1_inst/best`（run 1），不是 run 2 ep30。用它當基準會讓 RPE-rot 的 +6% 退步看起來像 −15% 改善。**同協定重量一次基準只要 10 分鐘**，做了兩輪分析才發現。 |
| 2 | **診斷腳本的 `loss_camera` 無效** | `diag/ego_flow_residual.py` 早期版本用它當權重校準的分母，但 clip 未過 `trainer._process_batch` 的尺度正規化 → GT 平移是公尺、預測是正規化尺度，量到的是單位不符（5.67~36.8 vs 真值 0.0087，差三個數量級）。分母排序等於**場景公尺尺度**排序，就是那個 tell。該功能已移除。 |
| 3 | **warm start 不剝檔案 → 靜默空轉** | 完整 trainer checkpoint 帶 `prev_epoch=29`，`while self.epoch < self.max_epochs`（trainer.py:495）直接不進迴圈，**exit code 0、無 traceback、log 看起來正常結束**。用 `extract_weights.py` 剝成純權重。 |
| 4 | **`max_epochs` 定義排程長度** | LR 由 `where = exact_epoch / max_epochs` 驅動（trainer.py:821）。「先跑 20 再延長」不成立——跑完 LR 已是 1e-8，續訓等於不動，重開排程會再 warmup 一次把軌跡打散。**排程長度必須一開始就決定。** |
| 5 | **凍結不擋梯度穿透** | `freeze.py:88` 只設 `requires_grad=False`，梯度照樣穿過該模組流進上游解凍的層。要真正切斷深度路徑必須用 GT 深度或 `detach()`。 |
| 6 | **煙霧測試不釘 clip 形狀量不到峰值記憶體** | `DynamicBatchSampler` 從 `img_nums` 均勻抽長度、`batch = floor(16/S)`，影像數固定但 global attention 是 `B·(S·P)²` —— S=16 是 S=4 的 4 倍。20 步隨機抽很可能抽不到 16。要釘 `img_nums: [16,16]` + `aspects: [1.0,1.0]`。 |
| 7 | **depth 協定不一致（未解）** | 同一個 ckpt、兩邊都宣稱 `max_depth=80`：`benchmark/eval_sintel.py` 給 AbsRel **0.1842**、TTO 線的 `eval_model_depth_on_sintel` 給 **0.2209**，δ1 卻幾乎一樣（0.7188 vs 0.7151）。兩份文件的數字若要並列必須先查清楚。 |

| [`training/diag/train_health.py`](../training/diag/train_health.py) | 訓練健康紅綠燈（四關），只讀 `log.txt` 與 `pose_eval/`，可對執行中的 run 跑 |

### 兩個被實測否證、但程式保留的想法

- **`max_depth_ratio`（遠景截斷）** —— 假設 Waymo 佔 50% 目標函數是遠景造成的。掃描 ×10/×5/×3/×2 份量全部釘在 51%，而 Spring 反而更糟 → 殘差集中在**近景**（視差大處），砍遠景只是砍掉旋轉證據。真因是離群尾巴，`per_pixel_thre` 從 MonST3R 的 50（實測保留率 1.000，等於沒開）改成 5 就解決了。
- **`use_dynamic_mask` 在 GT target 下無作用** —— 見 5.5。理論在預測深度下被否證（誤差從預測端進來），在 GT 深度下成立，但實測影響落在雜訊帶內。
