# 回覆結構

- 一則回覆的固定順序：**① 一句話結論 → ② 需要你決定的事 → ③ 證據／數據 → ④ 背景與推理**。
  背景、原因、翻案理由一律放最後（必要時用 `---` 分隔線隔開當附錄），不要放在前面鋪陳。
- 超過兩個區塊時，**一定要用 `##` 標題把區塊切開**，不要全部黏成一串條列。
- 一則回覆最多做兩件事（例：報告＋提問）。翻案（推翻我上一輪的建議）、
  警告（會造成靜默錯誤的狀態）各自獨立成一個標題區塊，不可混進條列。
- 不要寫「依 CLAUDE.md 的規矩」「照你的要求」這類自我說明句，直接用固定標題標示。

## 固定標題

需要我確認或決定時，一律用這三個標題，不要自創別的說法：

- `【觀察】` —— 直接跑出來的數字或事實。附上依據（哪支 script、哪個 ckpt、哪個 split）。
- `【結論待確認】` —— 從觀察推導出的詮釋或主張。
- `【需要你決定】` —— 要我選的行動方案。有多個選項就標 A/B/C，並標明你建議哪個。

# 觀察 vs 結論

- **觀察** = 測量到的數字或事實，重跑一次會得到一樣的結果，沒有爭議空間 → 我只需要知道，不需要同意。
- **結論** = 從觀察推導出的詮釋、判斷、主張（例如「這個方法有效」「幅度不算雜訊」）→ 這才是要我確認的對象。
- **不要把觀察本身當成結論列出來要我同意。** 只有涉及詮釋跳躍的敘述才需要確認。
- 結論要寫成「基於上述觀察，我認為：⋯⋯」，把推論跳躍講明白，讓我能只審查那一步。

# 問句要自我完整

- 每個要我確認或決定的問句，**必須自己重述完整要點**，不可以用「上面」「剛才提到」
  「這個結論」等代稱指前文，即使內容剛剛才寫過。
- 判準：假設我只看到那一句話，也要能看懂在問什麼。

# 溝通風格

- 一到兩句話講完「做了什麼／發現了什麼」，細節和推理放在結論之後，用條列呈現，不要寫成大段落。
- 避免不必要的鋪陳、重複強調、過度解釋動機——直接講重點。
- 遇到專有名詞或術語：
  - 如果是研究/程式領域已有慣用中文譯名，才用中文，否則保留英文原文，
    不要自己即席直譯造詞（英文技術詞彙直接用英文：gate、loss、checkpoint、attention 等）。
  - 不確定中文譯名是否存在或是否常用時，寫英文原文＋簡短中文解釋，不要自創譯名。
- 專案內部代稱（`channel B`、`config header`、`inst_g`、warm start、「混血」等）
  **每則回覆首次出現時附一句話定義或指到檔案位置**，不預設我記得。
- 如果一個解釋預期會超過一段，先問我要不要看完整版本，還是只要重點摘要。

# 格式

- 同一個區塊只用一種格式：多筆同構資料 → 表格；不同性質的點 → 條列；因果推理 → 散文（最多三句）。
- 表格只放數字／對照，**不要在表格裡寫推理**。一則回覆最多一張表。
- 表格和條列不要夾在長句中間。

# 驗證與執行

**除非我明確說「可以直接測試」，否則任何驗證都要先讓我知道「為什麼要驗」和「具體怎麼做到」，等我同意才能執行。**

想驗證某個假設（跑 diag script、寫 debug 程式碼、查證某個猜測）之前，先講清楚五點：

1. **假設** —— 一句話，可證偽。
2. **為什麼要驗** —— 這個答案會改變哪個決定。
3. **方法** —— 條列步驟，寫清楚「輸入哪來 → 算什麼 → 輸出什麼數字」。
   優先用 `training/diag/` 或 `training/benchmark/` 現成的 script，現成的做不到才寫新程式。
4. **判準** —— 事前寫死：假設成立會看到 A，不成立會看到 B，含門檻數字。
   事後才決定怎麼解讀數字不算數。
5. **成本** —— 大概跑多久、要不要 GPU。

其他硬規則：

- **先給計畫，不要先給程式碼。** 上面五點你同意之後才開始寫實作。
- **複雜度上限**：新驗證程式超過約 50 行、或需要新 dependency／新資料前處理，
  先停下來說明為什麼需要這麼複雜，等我同意。
- **寫完 script、執行之前**，再給一次 5 行以內的說明：這支程式讀什麼、算什麼、
  印出來的每個數字是什麼意思。
- 一次性的驗證程式寫在 scratchpad，不進 repo；我說「這個要留著」才搬進 `training/diag/`。
- 一律先把指令印出來，等我確認後才執行。
- 短的 smoke test 可以跑，但不要直接跑長時間程式（完整訓練／長時間 eval）。
- 我沒有明確回覆（同意／反對／修正）前，視為尚未確認，不要自行延續，
  也不可以把未確認的結論當既定事實用在後續的程式碼或實驗設計決策中。
- 例外：唯讀、無副作用的查詢（看檔案內容、跑不影響專案狀態的指令）不受上述限制。

# 視覺化

- 不要使用 `plt.show()`。
- 每張產生的圖都要存在 repo 裡面。
- 存檔後把圖片路徑印出來。

# 輸出路徑

依「誰寫入」分成兩個目的地：

- `training/logs/<exp>/` —— **只放訓練產物**：`ckpts/`、`tensorboard/`、`log.txt`、trainer 自己的 `pose_eval/`。
- `outputs/<tool>/<exp>/` —— **訓練之後產生的一切**：benchmark 數字、ablation json、診斷、圖。

`<exp>` 由 ckpt 推導，一律走 `eval_utils/paths.py`（`default_output_dir(ckpt, TOOL)`，或給沒有 ckpt 的 caller 用 `output_dir_for_exp(exp_name, TOOL)`）——**不要自己拼路徑**。`<exp>` 這層讓圖自帶 ckpt 身分，換 ckpt 重跑不會靜默覆蓋，圖和 json 也能用同一把鑰匙對起來。
